## 阶段 4 · 局部形变（21:05–21:25）

双缓冲（base + offset）+ `(1-d/R)²` 衰减 + 稀疏撤销栈 + BVH refit。

**踩到的两个真实 bug**（都由自动化测试发现，不是靠肉眼）：

1. `Vector3.transformDirection()` 会把向量**归一化**，位移的幅值被抹掉。改为提取逆矩阵的线性部分用 `applyMatrix3()`。
   → 测试断言「顶点位置总和变化 0.0000」暴露了它。
2. 没有位移上限。一次 0.8 秒的按住把顶点推出 1.6 世界单位，在 1.2 单位的椅子上拉出一根贯穿画面的尖刺（截图见 `test-artifacts/23-sculpted-model.png` 的历史版本）。
   → 加 `0.34 × boundingSphere.radius` 上限，并把速率从 1.35 降到 0.55。

## 阶段 12 · 手势交互层（2026-11-15 16:00–17:30）

真机试用的四条反馈，逐条核实后归因如下。**没有一条是"做了但指标不达标"，全是"功能没做"或"标准没定义"**，这本身说明阶段 11 的验收表有系统性偏差：它量化了系统内部能测的量，没有量化用户要的东西。

| 反馈 | 核实结果 | 归因 |

## 阶段 13 · 手势指针覆盖全部控件类型（2026-11-15 17:00–18:10）

标准变更说明：`06-feature-acceptance.md` 重写为 v2.0。判定从"指标达标"改成"这件事能不能做到"，
56 条 → 61 条能力条目。阶段 11 的量化表降级为附录，数字不再参与判定。

为什么先做这一件：阶段 12 把"手能点按钮"做出来了，但**只有 button 这一种控件能用**。
14 类控件里 5 类可用、9 类不可用——滑杆拖不动、行内图标点不到、下拉选不了、文件框打不开、面板滚不动。
用户要的是"手指控制整个屏幕"，而屏幕上一半的控件是指针够不着的，这条链就是断的。

本轮只做这一件事，不碰视角手势（Ⅰ-5 留给下一轮）。

| 缺口 | 根因 | 做法 |
|---|---|---|
| 滑杆拖不动 | 手势只有 click 语义，滑杆需要"按住并移动"，而合成事件不会触发原生拖动 | 自己算：捏合 = 开始拖动，指针横坐标 → 轨道矩形线性映射 → 原生 setter + `input` 事件写回 React；松开派发 `change`。拖动时轨道亮框、光标变实心、下方显示实时数值 |
| 行内图标点不到 | 命中层 `closest()` 只到 `.obj-item`，三个 mini 图标没有独立命中目标 | 图标加 `[data-hand-hit]`，命中解析改为"最内层优先"；命中盒 18→24px |
| 小控件点不准 | 手指精度不如鼠标 | 磁性吸附：指针空点时，在 8/16px 两圈共 16 个方向上找最近的可点控件，只吸附高度 ≤32px 的小控件（大按钮必须直接命中，否则画线时会被工具栏吸走） |
| 面板滚不动 | 没有滚动语义 | 面板空白处捏合上下拖 = 滚 `scrollTop`，虚线框提示；滚动容器内关闭磁性吸附，否则每个空白点都会被吸到按钮上 |
| 下拉选不了 | 原生 select 弹层不接受合成点击 | 风格旁加「风格 xx」循环按钮，点一次切下一个 |
| 取色器打不开 | 系统弹窗 | 加 8 个预设色块按钮 |
| 生成必须打字 | 没有输入法 | 「生成」工具下给 4 条短语胶囊（珊瑚椅/雪山/青瓷猫/赛博街灯），点一下填入 |
| 隔着面板点到后面物体 | 只判 `overUi`，面板空白区算"没压到 UI" | 新增 `blockScene`：指针在控件、滚动区、面板/顶栏/工具栏/浮层任一皮面上，一律抑制 3D 拾取与落笔 |

两个踩过的坑：

## 阶段 14 · 整页卡顿：把推理搬出主线程（2026-11-16 17:40–19:10）

用户反馈："整个页面全部的内容全部都是卡的"。先测，不改。

**测量（同一台机器，Chrome 有头 + 真实 GPU = Intel UHD）**

| 状态 | rAF p50 | 整页帧率 |
|---|---|---|
| 启动浮层 | 16.7ms | 60 |
| 鼠标模式（无摄像头） | 16.7ms | 60 |
| 开启摄像头（旧实现） | **33.3ms** | **30** |

CPU 采样（4s，200µs 间隔）指向唯一热点：`readPixels` 占 **83.4%**。
这是 MediaPipe GPU delegate 每帧把结果张量从 GPU 拉回 CPU，**同步**、单次 20–30ms，
在集成显卡上等于每 33ms 冻结一次主线程——所以面板滚动、光标、悬停全都跟着卡。

**修复**

| 改动 | 说明 |
|---|---|
| 新增 `src/lib/handWorker.ts` | 推理整体搬进 Web Worker；主线程只做 `createImageBitmap`（异步约 1ms）+ 结果换算（<0.1ms） |
| `handTracker.ts` 重写 | 取帧循环改为"有在途结果就丢帧"，自适应降频；滤波器/捏合/五指判定仍留在主线程（纯数值，成本可忽略） |
| `vite.config.ts` 加 `worker.format = "iife"` | 见下 |
| `CameraPanel` 姿态回显 | 文字没变就不写 DOM（每秒 122 次变更 → 9 次） |
| `PointerCursor` | 去掉逐帧 `new Plane/Vector3/Raycaster`（每秒约 300 个垃圾对象） |

**为什么 Worker 的加载方式这么绕**：MediaPipe 的 wasm 加载器是 UMD 工厂，靠
`importScripts()` 或 `document.createElement("script")` 挂全局 `ModuleFactory`。
Vite dev 只产出 **module worker**：没有 document，`importScripts` 存在但抛 TypeError，
退回到 `import(url)` 后 module 作用域里的 `var` 又不会变成全局，最终报
`Failed to fetch dynamically imported module: .../vision_wasm_internal.js?import`。
解法是 worker 自己 fetch 加载器源码、用间接 `eval` 在全局作用域执行，再给 MediaPipe
一个空 loader 占位跳过它自己的加载逻辑。生产构建是 iife 经典 worker，同一条路也成立。

**修复后测量**

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 整页 rAF p50 | 33.3ms（30fps） | **16.6ms（60fps）** |
| 主线程 readPixels | 占 CPU 83% | 0（在 worker 线程） |
| 每秒 DOM 变更 | 122 | 9 |
| 推理单帧 | 33–35ms（阻塞主线程） | 33–35ms（只在 worker 线程）→ 有效检测约 20–23fps |
| 检测帧率上限 | 30fps（被主线程卡住） | 由 worker 吞吐决定，慢时自动丢帧不排队 |

说明：推理本身的 33ms 没变，变的是**它不再占用主线程**。想再快只能换模型或降 `numHands`，
不属于"卡顿"范畴，暂不动。

回归：`bench:features` 29/29、`bench:hand` 12/12、`bench:gesture` 全绿、`build` 通过。

## 阶段 15 · 手消失 + 不跟手：时间基准与帧流水线（2026-11-16 19:25–20:20）

用户真机反馈三条：①"之前能显示手掌，现在显示不了"；②"识别太慢，手稍微动一下就识别不到"；
③"我只能用鼠标点，手不知道去屏幕哪里了"。

**根因：一个时间基准错误，同时造出前三条里的两条半。**

MediaPipe 推理搬进 Worker 之后（阶段 14），`ingest()` 收到的是 Worker 侧的 `performance.now()`。
Worker 的 `timeOrigin` 是 Worker 创建时刻，实测与主线程差 **4106ms**。而下游两个地方都按
"主线程时钟 - updatedAt < 450" 判数据是否新鲜：

- `HandRig.tsx` → 3D 手永远不显示
- `Interaction.tsx` → `handFresh = false` → 回退鼠标指针、手势点击层 `source !== "hand"` 直接清空

于是：手不见了、光标不见了、手点不到界面、只能用鼠标。三件事一个因。

**为什么基准没抓到**：`bench-hand` 自己伪造 `handState.updatedAt = performance.now()`（主线程时钟），
绕过了唯一会出错的那一段。这是基准设计缺陷——注入型断言只能测"注入之后"的下游。
已补 `CAM-003`：真实推理链路下断言 `now - updatedAt < 300ms`，走真 Worker、真模型，专门锁这条回归。

**跟手问题的三处改动**：

| 项 | 改前 | 改后 |
|---|---|---|
| 丢帧策略 | `inFlight` 期间直接丢帧，延迟 = 2×推理 | 只保留最新一帧排队，结果回来立刻发，延迟恒定 1×推理 |
| 一欧元滤波 beta | 0.03（几乎不随速度变化，恒在 2.2Hz，每帧只吃 30% 位移） | 1.1（快速移动时多给 1~3Hz，滞后约减半） |
| 跟踪阈值 | detection/presence 0.55、tracking 0.55 | 0.5 / 0.5 / 0.4（快速挥手不再判"跟丢"重做整帧检测） |

**delegate 取舍（Intel UHD 实测）**：CPU 51.9ms / 18.8fps，GPU 33.1ms / 28.4fps（渲染 60→45）。
选 GPU：检测率高 1.5 倍，45fps 渲染仍够用。可用 `localStorage.sc_delegate = "CPU"` 强制另一条。
输入分辨率 640×360 与 320×180 实测都是 33–35ms，**瓶颈不在输入像素数**，回到 640×360 保精度。

**补了两处视觉**：
- 掌面：腕 + 四个指根（0/5/9/13/17）的三角扇，半透明发光。之前只有骨线，五根线汇到一个点，看起来像烟花不像手。
- 丢帧兜底：检测偶尔丢 1~2 帧时用最后一帧姿态顶着并压暗到 0.35，手不再"闪一下就消失"。

回归：`bench:features` 30/30（新增 CAM-003）、`bench:hand` 12/12、`bench:gesture` 全绿。
